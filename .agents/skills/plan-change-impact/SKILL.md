# 需求影响与实施规划

将本次需求及受影响部分连成可交付的完整流程，再选择实施顺序。范围限定于用户目标，不重新设计整个项目。

## 建立整体判断

读取项目规则、当前需求／设计与已有任务账本；沿真实入口及调用链核对现状。区分用户要求、已有实现、已验证事实与未知，不能从旧完成报告推定当前版本仍有效。

围绕用户最终要完成的连续操作梳理：

- 受影响页面、接口、任务所有者、持久数据、授权、运行组件及必须保留的既有行为。
- 各要求的上下游依赖。对每个可能阻断交付的依赖标明现有证据或未知，特别检查“上游尚无真实产物，下游只能用夹具验证”的情况。
- 需求完成所需的证据：功能测试、真实集成、实际窗口、模型质量和发布包各证明什么，不相互代替。

对简单变更用一段话即可；不要为了填表展开无关模块。信息从代码和连接源可获得时先自行核对，只有影响范围或产品取舍无法确定时才询问用户。

## 用未知决定顺序

选出最可能使方案无法成立的未知，设计能实际消除它的最小步骤：接口／SDK／打包运行时未知，优先做真实集成探测；整页结构未知，先看完整页面；迁移未知，先只读盘点和隔离演练。不要固定为“先UI”或“先调用模型”。

探测必须达到该未知所在的层次。模拟协议不能证明实际SDK兼容；一条成功产物也不证明完整质量或故障矩阵。探测后继续完成原需求，不把最小链路当作缩减后的交付目标。

按依赖安排连续场景、集中实现和定向检查，再冻结候选、集成验收。复用现有工具与环境；提前识别需要用户参与的登录、信任或产品决策，明确其影响范围，同时推进已授权且不依赖它的工作。

## 留下可继续执行的结果

优先更新现有任务／交付账本或项目模板，不另建重复状态库。建议最小内容：

1. 目标、验收标准、不做范围与需求／设计基线。
2. 要求 → 受影响部分 → 依赖与已证／未知 → 完成证据。
3. 关键未知、首先执行的步骤及选择依据。
4. 后续连续场景、开发顺序和受影响回归。
5. 需保留的数据／行为、已有缺陷及停止边界。
6. 临时资源所有者、后续消费者、保留方式与清理时点。

新证据改变依赖、范围或方案时，更新这份判断和后续顺序；不要每轮重复改写通用规范。规则与阈值从当前项目读取，不把某次事故或项目约定提升为通用要求。
