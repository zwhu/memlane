- 原目标：交付新GUI并保留至少100 GiB开发空间；复用原运行服务，不迁移helper。
- 实际故障：最新保留包切换到build/mvp后，受管命令收尾将旧015后台所属完整.app当作旧构建删除。新GUI并不包含helper，实际仍依赖旧包；不能把GUI更新视为完整运行时替代。
- 已证原因：只保留最新包，没有保留完整依赖集合；进程命令仅显示memlaned，原清理逻辑没有识别所属.app。触发报告build/disk-cleanup/20261111-183406.json。属于执行及资源所有权管理错误，不能归因于用户空间要求。
- 影响：现有daemon76077仍运行，材料/知识可读；原memlaned和CLI按原SHA恢复，但完整包、资源和签名未恢复，重启/重登录后的恢复未知。不能声称数据可读就代表后台可恢复。
- 已做安全收尾：原字节恢复、显式保留依赖清单、lsof映射保护，5项隔离磁盘测试通过；没有重启/注册/替换helper。证据见build/mvp/debug/recovery-original-receipt.json、disk-safety-test-002.log和docs/ui-redesign/mvp-delivery-audit-20261111.md。

## 防复发硬规则

1. 最新GUI包不等于完整运行时。清理前盘点GUI、daemon/helper、Agent桥接路径、服务注册路径、组件及模型的实际引用；保护仍被引用的完整所属包、资源及签名，不能只保护可执行文件。
2. 修改保留包指针时，同步维护依赖清单；不能先丢失旧依赖保护再补登记。运行进程映射是补充证据，不能仅凭ps命令名或没有进程判定可删除（还可能被服务或Agent配置引用）。
3. 只有完成真实依赖迁移并验证后，旧包才能成为可清理候选；依赖关系未知时保留并报告。空间不足且无安全候选则停止构建/下载，不删除必要依赖凑空间。
4. 开发临时清理与用户主动卸载分开：卸载需要明确资源所有权、共享依赖、用户数据选择与结果回执；不能将用户数据或其他程序资源归入可再生缓存。
