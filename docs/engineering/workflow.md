# 工程规范

2026-11-11 起实施；不改变产品、授权、设计和100 GiB磁盘规则。

## 开发节奏

通用影响分析与排序方法已抽到 [plan-change-impact](../../.agents/skills/plan-change-impact/SKILL.md)。本项目使用[任务说明模板](task-brief-template.md)，写入现有任务／交付账本；产品与设计以对应已确认交接为准。

1. 编码前明确用户主流程、真实入口、前置条件、预期数据变化、不允许变化和证据位置。用例先于代码；诊断问题先复现再修。
2. 集中修改同一类问题。实施期间运行受影响包、编译和静态检查；授权越界、数据破坏、编译错误和主流程阻断立即修复。
3. 源码冻结后统一全量test/vet、组件冻结和完整App构建。记录输入摘要、版本和退出码；不为每个间距或文案变更全量打包。
4. 同一合成根连续验收。失败保留原回执，按根因类别集中修复和复验；新操作使用新ID，不能覆盖旧失败。
5. 功能、UI、运行包分别登记。源码测试、协议夹具、模拟窗口、真实Native、实际模型各自只证明对应边界。

## 同一问题反复验收失败的停止规则

用户2026-11-11明确要求：同一问题如果超过3次验收未通过，可能是产品设计的问题，不用一直尝试，记录下来汇报。

2026-11-12用户纠正：不同类型的问题不能累计成同一问题4次，并要求同步修改规则。以下按具体问题计数，不按整项交付的失败总数计数。“连续4次”不再表示连续4轮整体验收失败；四轮分别暴露不同缺陷时，各缺陷分别计数，不触发整项交付停止。

计数示例：四轮分别发现布局、复制、焦点和来源权限问题，各问题分别记1次，不触发“四次失败停止”。同一具体缺陷即使中间穿插其他问题，累计第4次失败仍须停止该缺陷；停止范围限于该问题及确实依赖它的工作。

- 同一问题累计第4次验收仍未通过，即停止继续针对该问题的实现尝试、实验和验收重跑，先记录并向用户汇报；不自动开始第5次。新操作ID、包版本、运行路径、Agent或错误表述变化不能重置同一问题的累计次数。
- **同一问题的识别**：记录触发条件、失败现象、验收标准及证据；围绕同一缺陷的多次修复失败继续累计。整个Goal、页面、功能、包或测试命令不作为问题身份；“都属于UI”“整包又失败”不足以合并计数。根因未知不等于所有失败同源，也不得仅因换了根因假设就拆分同一缺陷。
- **不同问题分别记录**：验收夹具／方法错误、修复引入的独立兼容回归、不同页面的布局缺陷等，若触发条件、失败现象及修复对象不同，分别追踪；夹具错误不计为被测产品缺陷又失败一次。若后续证据证明同源，合并时去重同一验收轮次；若发现误合并，保留原记录、归类依据与纠正过程，不删除失败证据。
- **触发停止前核对**：逐轮核对四次是否确实验证同一具体问题。报告必须给出关联依据；不能仅列四个失败的命令或窗口就宣布达到阈值。分类未明先查现有证据，不擅自扩大停止范围。
- 不直接认定产品设计错误。检查产品设计、技术方案、实现和验收方法是否存在问题，区分已证事实、假设与未知。
- 汇报至少包含：原目标／验收标准、累计失败次数、每次版本与结果及证据、已经尝试的方案、未证实的原因、影响与保留数据、设计或方案疑点、待用户决策项。
- 停止后可整理已有证据、执行必要安全收尾，并推进不依赖该问题的其他工作；不得以“诊断”“换路径”“换模型”名义继续同一问题的尝试。等待用户明确后续方向后再恢复，原失败记录和计数保留。
- 次数指针对同一问题的验收轮次；同一轮的多个断言或定向单测不重复计次，也不能用拆分、改名或合并记录掩盖已失败的验收轮次。

## Go与MyGo

工具链固定Go 1.27.3、MyGo v0.7.4，以go.mod/go.sum和scripts/go.sh为准，不改系统默认环境。当前锁版本静态检查采用该Go工具链的gofmt与go vet；尚未引入第三方lint，不能写成已配置golangci-lint。

改动Go文件先gofmt，再以 `sh scripts/go.sh vet ./受影响包` 和定向测试检查；集成门禁为 `sh scripts/go.sh test ./...`、`sh scripts/go.sh vet ./...`。有并发所有权变更时对受影响包运行race，不重复无关全矩阵。

UI组件保持稳定Key，异步结果核对项目／配置代次和当前操作。任务归daemon所有；UI动效只表达真实状态。布局用实际可用宽度，长正文独立滚动、操作可达；保存与启用、知识与原文分离。实际普通／窄窗口、焦点、草稿、返回路径仍须Native验证。

## 留证契约

UI动作→IPC请求→后台任务→模型网关各层关联操作ID／任务ID与阶段。保留失败阶段、固定安全原因码、HTTP状态、配置代次及耗时；前置拒绝也需要明确可观测边界，不能只记录成功或模型启动后的错误。

错误链仅保留允许的结构化安全码，不复制raw Error、正文、schema、认证、用户路径或provider响应。每层记录容量上限和准入规则；未知保持unknown。请求观察数不是模型次数，completion标签不证明启动；Process缺失不证明已回收。安全外层错误码和内部有限原因链分别记录，不由时间长短猜根因。

## Harness复用

通用验收设计、证据审阅与缺陷归类方法已抽到 [verify-continuous-scenarios](../../.agents/skills/verify-continuous-scenarios/SKILL.md)。本项目命令编排见[run-scenario使用说明](scenario-runner.md)，复用task.py磁盘门禁。现有具体驱动按任务逐步接入，不把新入口描述为全部Native验收已统一；失败阈值及停止范围继续按上文执行。

优先复用现有MyGo Tester／headless组件测试、e2e automation、IPC与实际窗口驱动，不搭另一套UI引擎。`scripts/verify-window.py`含旧“全部记忆”等导航，仅作协议参考，未迁移前不能用作当前设计通过证据。普通包不能携带e2e探针。

每个驱动须校验synthetic_only标记、bundle/root、实际可执行文件与版本；输出阶段结果和证据，超时不得静默重跑收费任务。数据库快照与进程退出分别验证；不要把无窗口capture当实际Native截图。当前统一Harness尚未完成，见清单。

## 真实缺陷记录与后台刷新（用户2026-11-12要求）

- 精简版已发生的问题见[分类错误与防复发索引](client-simplification-errors-20261113.md)，含机器可读条目、原文及脱敏证据归档。追加同一问题沿用原编号和累计次数；记录时区分已修复、配置规避、原因未知、风险防护及待决策项。
- UI 弹框、菜单与表单实施前，先查[组件使用经验](ui-component-lessons-20261114.md)：优先复用固定 SDK 的官方成品组件，统一主题与动效；使用 Base 需明确缺口并形成可复用封装，完成实际 Native 视觉核对后再报告交付。

- 用户要求：“这种bug都要记录下来，作为后续的指导”。真实缺陷修复后，按本目录复盘模板留下症状、触发条件、已证根因、修复边界、回归证据与未完成项，并从工程规范链接到记录；不能只留聊天结论或将未验证推测写成根因。
- 已有同范围、同来源的已核验数据时，后台轮询不应因请求进行中就卸载正文、清空列表数量或切换到整块加载页。首次加载与刷新已有数据需要区别处理。
- 原文授权／来源核验继续执行。收到权限撤销、版本变化、来源缺失或读取失败回执后，及时撤下失效正文与复制入口；不能用“防闪烁”保留已失效内容。切换项目／来源、过期异步回调仍遵守身份与代次隔离。
- 回归至少覆盖首次加载、连续刷新保持正文和数量、相同结果保持阅读窗口，以及权限／来源失效后不可读不可复制；源码测试与实际窗口观察分别记录。
- 本次实例：[原始记录后台刷新闪烁](reading-refresh-flicker-20261112.md)。
- SDK导入也可能有文件副作用；真实SDK验证须核对独立日志／缓存根，使用专用子进程HOME与cwd、显式日志设置并排除凭据，不以临时数据库根代替完整隔离。实例：[SDK日志隔离缺陷](cognee-sdk-log-isolation-incident-20261112.md)。
- 密码清空须同时核对业务字段、画面与真实Native辅助功能值；视觉遮罩不证明旧输入控件已释放。实例：[Provider密钥输入残留](provider-key-native-clear-20261114.md)。
- 新宿主工具记录复用官方trace构造器，保持字典参数契约；正常退出、采集事件回执不能替代队列排空和新会话采用。实例：[pi / TraeX工具参数不匹配](agent-trace-schema-20261114.md)。
- 小Schema探针通过不能代替官方整理的知识质量；真链无知识时保留gate／judge和样本适用性的未知。实例：[pi知识与新会话采用未通过](agent-knowledge-quality-20261114.md)。
- 精确文本断言须用无歧义的样本边界；先核对实际返回与指令，不把样本的句末歧义归为接口不支持。实例：[普通文本探针样本](generation-plain-probe-fixture-20261114.md)。
- 新宿主复用官方运行时须保留项目初始化与实际导入顺序，核对写入node_set和召回scope一致。实例：[项目标签不一致](agent-project-scope-20261114.md)、[TraeX事件契约](traex-event-contract-20261114.md)。
- 原生安装成功后核对实际cache摘要与启用入口；升级验证旧代文件仍可用，不能以源目录不可变推定宿主cache不可变。实例：[TraeX缓存与代际保护](traex-native-cache-20261114.md)。
- 实时策略明确拒绝与传输／策略未知分别返回，前者不能被通用异常出口标成未知，后者不能假定是权威403。实例：[新宿主权限回执](agent-policy-replies-20261114.md)。
- 验证模型时核对完成状态、实际请求模式与事实，不能只检查JSON能否解析；较新的失败／未知不能被历史成功遮盖。实例：[生成模型验证边界](generation-probe-boundaries-20261114.md)。
- 宿主发现与模型认证分开；重开设置应读取已保存的原验证结果，不让“重新验证”成为找回错误的唯一方式。实例：[Native设置连续核对](native-settings-continuity-20261114.md)。
