# 新宿主缺少官方项目初始化导致召回为空

编号MA-RECALL01，真实新会话验收失败1轮，修复后第二轮通过；原失败计数保留，不与MA-KNOWLEDGE01的“未生成可接受知识”混计。

目标：普通编码产生官方知识后，同项目新会话收到并实际采用。修复前pi真实编码已将retry_limit的修复、4项测试基线和功能范围写为3条知识；逐项与合成源码／实际回归比对，限定None和整数输入，事实有依据。新会话却多次得到空注入，甚至主动recall仍为空；同一回合的多次工具查询只记这一轮失败。

只读诊断使用原pi子主体：按生产导入顺序执行时，当前自动项目标签的官方list_lessons返回0；显式空scope返回3。并非缺少知识或该主体无法读Data。官方_plugin_common在正确导入时启用auto项目标签；自有JSON helper只建立launch record，没有运行官方_project_memory.begin/prepare，写入使用空node_set，召回按auto标签过滤。

修复：在确定独立主体、绑定项目和launch record之后，补调用官方begin/prepare。官方能力探测、身份锁定、node_set写入和召回过滤均保持，不另建检索链、不放宽项目过滤，也不修改Cognee或原日常Codex产物。新增定向检查保持真实导入顺序，只合成服务能力确认；核对官方remember请求的node_set与召回project_scope一致。

首次诊断曾提前导入_coding_memory，使默认配置初始化时机改变，错误地观察到空scope。该结果已由生产顺序诊断替代，不能用来证明原召回可用，也不计作又一次宿主验收。诊断始终只读，没有迁移或重写知识。

原3条无标签的试验知识、原会话和失败回执保留，不自动打标签或重放。修复后继续在同库、同主体、同合成仓库进行新的正常编码步骤，以验证新写入与新会话召回的一致性；验收计数不因新会话、代际或后续编码步骤变化清零。旧试验材料不作为修复后自动采用已通过的证据。

复验：pi正常增加retry_options并实际运行7项回归，官方生成4条带相同auto项目标签的知识。新pi会话自动注入1630字符，未调用任何工具即准确说明规则、7项测试和验证命令。随后正常交互式TraeX会话同样自动采用这批知识（没有读文件或记忆查询），完成同仓跨主体共享。TraeX继续普通编码增加describe_retry、实际回归10项，官方生成2条带项目标签的知识；全新TraeX会话自动注入1886字符、工具0次，准确说明新函数规则与10项测试。参见[脱敏证据](evidence/multi-agent-development-20261114/real-coding-hosts.json)。
