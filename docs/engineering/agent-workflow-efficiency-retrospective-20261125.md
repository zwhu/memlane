# 多 Agent 研发与验收工作流耗时复盘与改进方案

- **日期**：2026-11-25
- **复盘样本**：`v0.1.0-beta.3` 研发、双独立代码审核与 UTM 实机验收全流程（对应本地提交 `ce205ea`、`6b005c2`，执行窗口 `2026-11-24 21:28` – `2026-11-25 17:34`，共 188 条协同消息、累计活跃执行约 **890 分钟**）。
- **核心结论**：真正用于编写代码、打包和提交的时间仅占活跃总耗时的 **约 18%（~161 分钟）**；真正拖慢节奏的是 **无收敛上限的双审核拉锯（~280 分钟，约 31%）** 与 **UTM 重复搭环境 / 夹具插曲 / 网络与登录阻塞（~421 分钟，约 47%）**。

## 2. 六大慢点根因分析

### 根因 1：双审核缺少「代码分层口径」与「收敛上限」，把测试夹具当生产代码无限追轮
- **实证**：P1/P2/P3 修复中，所有 Go / Python 引擎与桌面端生产代码在第 3 轮就已达到零 P0 / 零 P1；但 R3→R7 仍连续消耗 **5 轮（47 分钟）**，只为反复打磨单个验收驱动脚本 `scripts/verify_setup_cli.py` 中仅在合成 mock 场景才会出现的轮询边角。第 7 轮甚至因复审提示词未重申第 2 轮已确认的契约例外，触发了一次纯形式上的 `REQUEST_CHANGES`。
- **机制缺陷**：
  1. 未区分「生产核心代码」与「测试/验收脚手架」的 P1 准入门槛；
  2. 无状态只读审查员（`--ephemeral`）每轮缺乏既有契约裁决摘要，容易围绕上一轮新补的防御代码继续递归挖边角；
  3. 已经 `APPROVE` 且其负责范围无新 diff 的一路审核员，后续每轮仍被重复唤醒参与同步等待。

### 根因 2：测试套件被多角色、多轮次重复全量执行
- **实证**：`go test -count=1 ./...` 单次耗时约 2.5 分钟（其中 `internal/bootstrap` ~60s、`internal/simpledesktop` ~37s、`memlane` ~33s），引擎模型回归约 2.3 分钟，`scripts/test_*.py` 约 20–30 秒。一次完整修改往往出现「编码 worker 全量跑一遍 → 审核员再全量跑一遍 → 提交 worker 提交前又跑一遍」，且在只改 1–2 个 Python 脚本的轮次里仍反复执行无关 Go 全量回归。

### 根因 3：UTM 缺少预热基线、前置自检与登录态保护，环境摩擦占去近一半时间
- **实证**：
  1. **缺少 Fail-Fast 网络与登录预检**：客体默认 DNS 异常（I-06）与宿主机代理切换会直接阻断 `Trae CN` 内网登录与模型请求，导致脚本多次干等 120 秒以上才判定卡住。
  2. **清理脚本误伤登录态**：上一轮 GUI 净室截图脚本清掉了客体 `~/Library/Application Support/Trae CN`，导致刚完成的内网登录丢失并额外等待人工重登。
  3. **每次测试重复冷建库**：同版本连续做多轮 UTM 验测时，每轮都执行「备份 `Memlane.app` → 安装 DMG → APFS 克隆 6 组件并重定位 venv → 冷启动建库 74–82s → teardown 还原」，重复开销极高。
  4. **夹具脚本临场手写易出错**：多次因临场拼脚本出现认证头 401、Python 动态导入报错、漏传 `--instance-id` 等非产品问题，被迫整轮重跑。

### 根因 4：单批次改动体量过大，放大跨模块联动返工半径
- **实证**：首轮一次性并行改动 **181 个文件（+25,109 行）**，把 TRAE 4 事件修复、Agent-First 三步向导、零 Skill Setup CLI、Option 2A 与 `beta.2` 自愈全部打进同一批再进双审。首轮审查一次性暴露 5 个 P0 与 16 个 P1，随后 4 个编码 worker 在 6 轮里反复互相牵动接口与测试。

### 根因 5：多层代理嵌套导致小任务调度开销高于执行本身
- **实证**：即便是追加 2 条文档 TODO 或执行一次 `git commit`，也经历了「主控写长 brief → 新建 worker 冷启动 → 再调用 `codex exec` 冷读代码 → 写回板面 → 主控读回执 → 销毁 worker」的链路；大任务修复中所有 worker 也必须等最慢一路完成后才能统一进入审查，产生串行长尾。

### 根因 6：纯逻辑/协议缺陷拖到重型 UTM 阶段才暴露
- **实证**：本次在 UTM 实机才发现的 3 个真实缺陷——组件齐备时 `install --apply --wait 55` 同步超时（[install.go](../../internal/setupcli/install.go)）、已装未登录 CLI 导致 `/v1/generation` 返回空 `agent_bridges` 引发误报（原 `engine/python/agent_bridge_runtime.py`）、`repair --apply` 丢失 `preserved_third_party_groups`（原 `engine/python/trae_hooks_migration.py`）——本质都是**无须 macOS 虚拟机即可在本地 10 秒复现的契约问题**。因早期单测过度 mock 了对应边界，才推迟到耗时 2 小时的 UTM 阶段暴露。

## 3. 可落地的改进方案

### 改进 1：双审核引入「分层 P1 标准 + 2+1 收敛上限 + 增量免复审」
1. **明确分层 P1 门槛**：
   - **生产代码**（`engine/python/`、`internal/`、`cmd/`、`scripts/build_release.py`、`scripts/dev.py`、`scripts/uninstall.py`）：保持严格零 P0 / 零 P1 门禁。
   - **测试与验收脚手架**（`*_test.go`、`test_*.py`、`scripts/verify_setup_cli.py`）：仅将「会产出假绿、掩盖真实产品缺陷、破坏运行环境或泄露凭据」的问题定级为 P1；纯合成 mock 边角统一归为 P2，记录后不阻断交付。
2. **实行「2 轮修复 + 第 3 轮主控裁决」上限**：
   - Round 1：双路独立全量对抗审查 → 主控去重合并两份报告，一次性下发修复。
   - Round 2：双路只审查 **R1 问题闭环 + 本轮改动新引入回归**（提供 `git diff <r1_ref>` 与已确认契约例外清单，禁止无上下文重读全仓或推翻既有产品裁决）。
   - 若 Round 2 后仅剩非核心脚手架边角或契约口径分歧，不再开启 R3–R7 拉锯，由主控结合实测事实直接裁决收口。
3. **单路已通过免重复唤醒**：若某一路审核员已 `APPROVE` 且其覆盖语言/模块后续无新改动，不再唤醒重复复核或重跑无关全量测试。

### 改进 2：测试执行分层与单一归属（对齐 [工程规范](workflow.md)）
1. **开发与审改轮只跑受影响包**：
   - 仅改 `scripts/verify_setup_cli.py` → 只跑 `test_verify_setup_cli.py` + `scripts/lint.py`（< 5 秒）；
   - 仅改 `internal/simpledesktop/` → 只跑 `go test ./internal/simpledesktop/...` + `scripts/lint.py`；
   - 仅改 `engine/python/` 某模块 → 只跑对应 `test_*.py` + 模型回归（仅修改模型链路时）。
2. **全量门禁集中在「冻结后、打包/提交前」执行一次**：由单一验证节点执行 `sh scripts/go.sh vet ./... && sh scripts/go.sh test -count=1 ./...`、`scripts/lint.py` 与 `scripts/test_*.py`，审核员专注代码审查与轻量定向复现，杜绝「编码/审核/提交」三方重复跑全量套件。
3. **单测加速专项（后续排期）**：排查 `internal/bootstrap`（~60s）与引擎模型回归（~136s）中的串行等待与固定超时，目标将全量 Go+Python 集成测试压缩到 60 秒以内。

### 改进 3：UTM 实机验收标准化（Fail-Fast + 保护白名单 + 热环境复用）
1. **3 秒前置自检（Fail-Fast）**：任何客体脚本执行前，先在 5 秒内完成三项探针——① 目标域名解析与代理状态（检测 I-06 / 宿主机代理冲突）；② 磁盘余量；③ 目标宿主登录态凭证存在性（如 `~/.trae-cn/trae-jwt-token`）。前置不通立即中止报错，不再盲等 120 秒。
2. **固化唯一可复用客体驱动，禁止临场手写脚本**：把 host bridge、APFS 克隆重定位、隔离 `--config`/`--component-root` 启动与结构化回执采集收敛为受测脚本；硬编码**不可触碰保护白名单**（`~/Library/Application Support/Memlane`、`~/Library/Application Support/Trae CN`、`/Applications/Trae CN.app`、`~/.trae-cn/trae-jwt-token`），任何截图或清理流程严禁触碰登录目录。
3. **支持同版本 `--keep-isolated` 热复用**：同一候选 DMG 连续执行多场景验测时，允许保留已就绪的隔离后台与组件目录，全部场景测完再统一 teardown，避免每轮重复耗时 ~80 秒冷建库。
4. **CLI 协议验收与 GUI 视觉验收解耦**：Level 1 流程（安装、中断、升级自愈、repair、权限矩阵）尽量走纯命令行/桥接非交互执行；仅将浅/深色截图与真实宿主 UI 点击交给 Computer Use。

### 改进 4：按纵向垂直切片拆分交付（单批 ≤ 30–40 文件）
- 遇到跨 Go / Python / UI 的大需求时，拆分为可独立编译、独立过测、独立提交的垂直切片（例如：`切片 1：后端契约与迁移` → `切片 2：CLI 与守护` → `切片 3：桌面端向导与动效`），每个切片单独走小 diff 双审与提交，避免 180+ 文件巨型 diff 造成 6 轮跨层震荡。

### 改进 5：精简编排层级，避免小任务重调度
- **按任务体量选调度方式**：
  - 确定性小任务（文档更新、单点小修、打包构建、本地提交）：直接执行或单步完成，不再走「主控 → 新建 worker → 再套 `codex exec`」三层嵌套；
  - 中大型并行开发与独立双审：继续保留多 Agent 并行，且支持先完工的解耦模块提前进入单侧审查（流水线化），不死等最慢分支。
- **复审提示词自带上下文锚点**：每次复审明确附带 `改动文件清单`、`本轮增量 diff 范围` 与 `已确认契约例外清单`，消除无状态审查员的重复扫描与误报。

### 改进 6：进 UTM 前增加 30 秒本地「无 Mock 契约冒烟」
- 在调用 [build_release.py](../../scripts/build_release.py) 打包后、上传 UTM 前，增加一道本地 `$TMPDIR` 真实二进制集成冒烟（不依赖 UTM、不碰日常库）：
  1. 用真实二进制覆盖「组件已齐备 + 慢初始化超过 `--wait`」路径，验证 `exit 20` 与 `worker_active=true`；
  2. 用真实控制服务覆盖「CLI 已安装但无默认模型配置」路径，验证 `/v1/generation`、`doctor` 与桌面端不误报「未安装」；
  3. 覆盖 `repair --dry-run` 与 `--apply` 关键统计字段（如 `preserved_third_party_groups`）一致性断言。
- 让逻辑和协议缺陷在本地 30 秒内暴露并修复，把昂贵的 UTM 实机时间留给签名、Gatekeeper、真实宿主应用集成与实窗视觉验收。
