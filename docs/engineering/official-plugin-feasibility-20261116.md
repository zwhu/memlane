## 输入与连续场景

- 插件基线：`a176248914fdb32a78354854b300174203b15a5c`，1.8.0；不是最新上游能力结论。
- 核验开始前逐文件匹配 `engine/patches/project-access-upstream.json`，直接调用缓存中的未修改官方源码。子进程禁止 pyc 写入，配置、状态和合成会话位于临时宿主目录，退出后清除。
- 合成 HTTP 场景：官方 skill 的 shell 保存入口 → 私有 env 配置 → 独立样例凭证 → dataset UUID → 本机 HTTP 接收／拒绝 → 官方回执。
- 合成采集场景：采集关闭期间写入样例问答 → 调用官方 capture → 开启采集并追加新问答 → 再调用 capture，观察原版解析及发送内容。
- 合成整理场景：两个官方自动整理参数均设0 → 调用会话结束使用的官方整理函数，观察其是否仍调用提交传输。
- 真实服务场景：读取现有日常服务中的 owner、Codex／TraeX 子主体、tenant／role／direct ACL，核对6个 verified 项目与当前管理策略。只做GET，不读正文，不创建新主体或数据组。

## 对补救顺序的影响

1. 已有证据支持优先将服务地址、私有配置、独立凭证和基本dataset选择从内部补丁改为官方配置；还要验证实际宿主能否正确传递这些配置。当前没有实施替换。
2. 官方 `config.get_dataset` 从会话launch记录或配置读取目标，不负责与Memlane项目登记表按工作目录绑定；项目解析仍需外层接入，不能把提供一个固定dataset当成自动项目归属已解决。
3. G01、G02先按真实规则缺口处理。下一步核对宿主公开hook编排是否能在官方脚本之外实施采集边界与处理准入。仅在外层调用原版解析函数、重写其游标仍可能依赖内部契约，不能描述为已经消除耦合。
4. 后台 `project_backlog_worker.py` 直接导入 `_plugin_common` 和 `_memlane_policy`，安装校验也强制要求后者存在。因此现在不能直接卸掉补丁并替换整个安装。
5. 后续真实保存要同时核对官方Data、原文读回与Memlane分类；此前已发现显式remember默认文档不一定归入当前记忆列表，见[显式记忆研究](../research-cognee-explicit-memory-20261116.md)。本轮未伪造session_learnings或改分类。
