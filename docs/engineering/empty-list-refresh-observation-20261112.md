# 空列表刷新切换遗漏

## 修复与同候选自验

此缺陷已在032／033开发候选完成源级回归和实际Native自验，范围限于项目列表空态，不把已有正文的旧证据外推为所有列表通过，也不宣布整个Goal完成。

### 已证原因与修复

- `loading`只说明有请求，不能说明页面没有已核验结果。新增只含身份的列表回执键，绑定当前库、页面和完整列表查询（项目、类型、筛选、排序、日期等，cursor不另分范围）；成功空结果同样留下回执，不复制正文或另建索引。
- 已核验空结果在后台请求／暂时失败时保留原空态和数量。首次有实际服务请求但无回执仍显示读取中；首次失败显示读取未完成，不假称空列表。记忆页故障在固定高度标题行显示“刷新未完成”与重试，恢复后消退，不用替换整块空态报告故障。
- 项目空知识引导还独立受`!loading`控制，曾让读取布局和右栏一起切换；现按同一有效回执保留。原重复错误说明块会抬高列表，已将记忆页故障反馈收进固定行，非记忆页反馈不变。
- 明确权限／来源失效清除回执、旧条目／选中／历史及数量，关闭失效来源阅读，显示不可读；保留用户未保存草稿。暂时失败与未知错误不被误作撤权。

### 正式回归

`reading_empty_refresh_test.go`复用现有IPC夹具，覆盖1200×820和800×620的普通原始记录空列表＋新增知识编辑器、项目空知识引导及筛选空结果。控制请求开始／完成，逐帧断言文字、Rect和阅读布局一致；同时覆盖暂时失败、恢复、scope_denied撤下、草稿保留、查询／页签／库隔离及首次失败未知状态。原overlay文件未改，原红和修复后日志均保留；静态overlay没有实际读取回执，正式IPC用例才用于证明首次未知与已核验空态的区别。

定向回归1.101s、desktop完整30.896s、定向race4.057s和desktop vet均exit0。日志在.local/empty-refresh-observation-20261112/并归档到下述证据目录。未重跑已因旧hook桥接失败停止的全仓test，原停止计数保留。

## 已证事实

- 此前[刷新复盘](reading-refresh-flicker-20261112.md)及009／011／017／020／021的连续Native证据主要覆盖已有会话／文档正文、数量、阅读位置和相关权限状态，不证明所有空列表状态稳定。
- 当前源码`library.go:refresh`每次请求先设置`a.loading=true`；`app.go`列表在`len(a.items)==0`时优先按loading显示“正在读取内容”，请求结束后再选择错误／空态。没有将已核验空结果与首次尚无结果分开。
- 在真实`App.View`上，构造与截图相同的通用“列表为空”分支，置loading并绘制下一帧，原空态文字消失。定向测试退出1：`confirmed: background loading withdrew the existing empty-state text`。这是源码复现基线，不是修复后验收失败，不自动并入旧正文闪烁的累计次数。

## 尚未证明与下一步

实际观察时原session已把同一运行App切换到两条官方知识及来源会话阅读页，未操作或切回其窗口；因此没有取得用户截图状态的Native连续帧，也没有证明该运行二进制与当前源码完全相同。不能把源码复现说成已证明截图抖动全部根因，更不能宣称已修好。

后续修复需明确区分首次未知、已核验空、暂时失败及明确权限／来源失效，避免用永远显示“空列表”掩盖首次加载或故障；再覆盖同一候选的正常轮询、故障恢复和实际窗口几何。产品状态未由本次修改，未停止或替换原session的App／服务。
