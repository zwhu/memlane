# Memlane Beta 安装问题清单

本清单记录 `v0.1.0-beta.1` 在 macOS 26.6.2 arm64 UTM 客体上的安装与 Pi 验收问题。测试使用当前源码构建的 `.app`。旧安装升级、空库首装和无缓存下载需要分别验收。正式发布标准见[首装发版门禁](workflow.md#首装发版门禁)。

## 问题与复验记录

| 编号 | 问题与证据 | 处理结果与待验项 |
| --- | --- | --- |
| I-01 | 旧 Agent 插件的固定补丁回执与当前清单不一致，安装预检判定插件不兼容。 | 核验官方归档 SHA256 和构建后的插件清单，原子更新插件路径并保留旧插件。组件复验通过，旧库整套启动见 I-05。 |
| I-02 | 已有 pi 配置，但独立真实模型探针 40 秒未返回。 | 同一账户在客体临时 DNS 下收到预期合成回复。应用内真实验证另见 I-13。 |
| I-03 | 客体下载固定 Agent 插件时报 `lookup gh-proxy.com: i/o timeout`。 | 宿主从官方路径下载，客体复核固定哈希和完整插件清单。手动恢复通过，原镜像路径待复验。 |
| I-04 | 修复插件后，旧库启动仍无可用后台。重试明确暴露 `OwnerRecord.generation_reference` 对象与字符串不兼容。 | 当轮归档回执后越过该阶段。当前写入端与读取端的正式契约修复见 I-16，原旧库整套升级仍待验。 |
| I-05 | 旧库整套启动第 4 轮仍返回 `generation_start_failed`，引擎未监听。客体同时出现 DNS 超时。 | 已达到停止阈值并暂停该旧库场景。保留旧库、插件和回执。具体验证或启动失败原因待证，净室通过不代表旧库升级通过。 |
| I-06 | UTM 默认 DNS 无法解析 GitHub、PyPI 和 DeepSeek 等域名，阻断首次下载和模型请求。 | 临时 DNS 对照恢复解析，测试后恢复原设置。客体默认 DNS 的长期修复仍待验证。 |
| I-07 | 国内源的 `uv` 下载停滞，Python 下载仍有进度但很慢。 | 向导停止后清理部分下载。手动补入两项固定归档并复核 SHA256，续跑通过。无缓存自动下载待复验。 |
| I-08 | 运行库安装到 OpenSSL 阶段时报 `artifact HTTP 403`。 | 两端核验固定归档后补入受管缓存，向导续跑解出 OpenSSL 动态库。原自动下载路径待复验。 |
| I-09 | 安装后首次运行库探测报 `installed component failed verification`，同一运行库独立导入原生依赖成功。 | 同版本只读探针复测约 9 秒；向导重新检测与续跑通过。首次失败的具体条件仍未知。 |
| I-10 | 向量模型自动下载约 2 MiB/分钟，首次安装等待过长。 | 通过向导取消，重新下载所有固定文件并逐项核对大小和 SHA256，再续跑通过离线模型验证。自动下载速度待复验。 |
| I-11 | 首装新库时报 `ModuleNotFoundError: No module named '_runtime_common'`。首装只准备了三个文件，遗漏运行依赖。 | 首装与运行共用经验证的包内资源。构建脚本从产物执行包内检查。UTM 同库续跑、重启和独立空库通过，续跑保留库标识和属主回执。 |
| I-12 | 向导允许选 Pi 作为待启用模型，但缺少必要的真实验证入口，无法点击「启用并完成」。 | 向导恢复已保存的候选并提供真实验证动作。UTM 实窗的普通调用、结构化调用和质量检查均通过。 |
| I-13 | 应用内 Pi 验证曾以 `provider_unavailable`／`pi_model_failed` 结束。默认 DNS 对照复现了连接超时且没有收到 HTTP 响应；初次失败的底层日志不足。 | 同一完整验证样本在临时 DNS 下获得两次 HTTP 200，三项检查通过。应用向导随后完成正式验证。默认网络问题仍见 I-06。 |
| I-14 | 验证子进程可在受校验的 Python 资源内生成 `__pycache__`，下次启动因额外文件被拒绝。 | 给真实子进程添加 `-B`，回归覆盖相邻模块导入。客体归档旧字节码后复验通过，验证后检查到的包内 Python 目录没有新增缓存。 |
| I-15 | 持久纯问答已被采集，但提炼报 `no_gated_entries`，没有可供召回的知识。 | 带实际工具操作的会话采集到 5 条轨迹并自动生成 2 条知识，新会话无工具调用即可从自动召回答出已保存的文件名。原文中的重试时限、校验码及幂等键约束未进入知识，提炼保真仍待定位。 |
| I-16 | Pi 后台启用已完成，向导仍等待直至超时。重试显示 Python 写入的模型引用是对象，Go 按字符串读取，导致回执整体解码失败。 | Go 统一按 `id`、`revision` 读取。定向回归先复现问题再通过，继续拒绝外来属主和过期进程。UTM 原库直接进总览，独立空库首次点击启用后也自动进总览。 |

## 旧库完整启动的四轮结果

目标是在旧库上启动 Cognee 与接入网关、读回原项目，然后验收 Pi 的采集、提炼和跨会话召回。

1. `b1d10d1` 的 `.app` 显示插件与固定清单不兼容。引擎和网关均拒绝连接，属主锁空闲。
2. 同一候选手动补齐并校验插件后，重启等待约 80 秒，仍无后台监听。启动日志没有新记录。
3. 同一启动入口读取旧属主回执时返回 `generation_reference` 解码失败，保留原回执与原库。
4. `b1d10d1` 加当时的字段兼容补丁构建，候选指纹 `6c9164bd…`。归档旧回执后出现新启动日志，报 `generation_start_failed`，观察约 130 秒仍无引擎监听。

四轮均未达成旧库完整启动，旧库、插件与回执均保留。DNS 超时和模型配置仍是待区分的因素。后续改用空库验收 Pi，旧库升级待重新确认验收方向。

## 验收边界

- 含 I-16 修复的 `.app` 可执行文件 SHA256 为 `8cb0d7719dd2e69a11b89ad9d5f604632b60bb333de9b0528dea4dd5f790bf16`。包内首装检查和两端验签通过。独立空库在已核验组件上完成真实 Pi 验证、启用和总览跳转。原测试库、后台进程和启用操作均沿用原身份。
- 会话采集以可回读的持久会话与工具轨迹为准。此前一次无会话保存的 Pi 探针只验证了模型响应，当轮目录回读未找到该探针，另有一条命中来自更早的持久会话。
- 原测试库总览后来显示一条提炼失败活动 `CogneeSystemError`。尚未取得该活动的底层原因或确认其与前述提炼保真问题相关。
- Go 全量串行复验通过。早期运行曾出现浅色画像性能波动和临时目录清理失败，两项定向复跑和后续全量运行均通过。
- Pi 提炼细节保真、旧库完整升级、默认网络下从零自动下载与 DMG 安装仍有独立验收项。
