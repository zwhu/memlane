# 单人记忆库：本地、Docker 与远程部署方向

2026-11-17。状态：记录本轮产品方向及最低成本兼容建议；当前优先走通本地方案，Docker 与远程尚未实施或验收。本记录不恢复历史全量 Goal，不改变现有问题的停止计数，不启动部署、迁移或新模型任务。

## 用户决定与产品定位

用户原话：

> 远程cognee和docker的方案先给我记录下来，我们先把本地方案走通
>
> 但是现在需要考虑的是，如果怎么设计方案，成本最低的兼容能本地和docker
>
> 不需要多租户，不要想太多
>
> 定位是单人agent记忆库

Memlane 定位为单人 Agent 记忆库。主要价值是简化安装与日常接入，复用已有受支持 Agent 的账号和模型，让用户无需为了处理记忆另配 Provider。已有自配 Provider 入口继续作为可选能力。本次不扩展多租户、组织或多人协作模型，已有项目及 Agent 权限不因这次讨论自动删除。

## 当前优先级：先完成本地流程

继续以现有本机 Cognee、唯一日常库及 Agent 接入为基础：正常编码 → 官方采集 → Cognee 处理 → App 阅读记忆与出处 → 新会话实际召回并使用。

安装目标按用户 2026-11-17 最新要求调整为：App 先检测已有 Python、Cognee、embedding 模型及其他依赖，兼容可用则直接复用；缺项先列明用途、版本、来源、大小和位置，询问用户是否安装，同意后才准备。已有不兼容时说明原因并允许改选或确认补装，不擅自升级、覆盖或重复安装。此为产品目标，不代表正式安装包已交付。当前仍沿用既有 dev 入口及验收边界。

## 本地与本机 Docker 的最低成本兼容建议

核心原则：同一套 Cognee 服务代码、现有必要的服务侧适配和 HTTP 接口；只让服务的启动位置与启停方式不同。优先沿用现有模块，不建设通用部署平台或多引擎抽象。

| 部分 | 本地方式 | 本机 Docker 方式 |
| --- | --- | --- |
| 桌面 App | 用户电脑 | 用户电脑，复用同一界面 |
| Agent 插件安装、账号发现 | 用户电脑 | 用户电脑，复用同一接入流程 |
| Agent 模型桥 | 用户电脑 | 用户电脑，增加容器到模型桥的访问适配 |
| Cognee 与服务侧 SDK/路由适配 | 本机独立 Python 环境 | 同版本容器镜像中的 Python 环境 |
| App/插件访问 Cognee | 本机 HTTP 地址 | 映射到本机的 HTTP 地址 |
| 内容数据 | Cognee 管理 | Cognee 管理，容器重建后数据保留 |

具体边界：

1. 安装与启动逻辑区分本地进程和本机容器；阅读、搜索、保存、来源及项目规则继续使用相同 API。
2. 容器只替代引擎运行位置。依赖 Cognee SDK 或引擎内部存储的已有适配随服务部署，例如完整来源会话读取路由；本机 Agent 的安装路径与登录状态不搬进容器。
3. 运行配置负责区分 App/插件访问的引擎地址，以及 Cognee 访问模型桥的地址。容器的 `127.0.0.1` 不是宿主机；不能仅更换启动命令便宣称兼容。
4. Docker Desktop 提供宿主机网络访问路径，但当前模型桥只监听 loopback。实际地址、监听范围、凭据及连通性需要专项核对，不先假定改为 `host.docker.internal` 就已完成，也不直接扩大为公网监听。
5. 每次只有一种方式承载日常引擎和内容库。切换方式不自动新建第二套日常库或重放材料；数据位置及迁移另行确认。
6. 连接语义保持一致：API 可达、原主体权限、实际采集/处理/召回分别验收。未知写入沿用原操作核对规则。

同一个 App 内选择运行方式是当前建议，不是已完成的安装界面设计。Docker 方式可以减小客户端携带的引擎体积，但镜像仍需下载；不能把小客户端包等同于总占用下降。

当前架构已确认的复用点与差异：

- `internal/simpledesktop/client.go` 已通过 HTTP 读写 Cognee。
- `engine/python/project_control.py` 的官方 API 客户端仅允许 loopback；本机 Docker 通过 loopback 端口映射可保留这个边界，直接远程 HTTPS 需要后续适配。
- `engine/python/session_history.py` 注册与 Cognee SDK 同进程的完整会话读取路由，镜像需要包含这类已有服务侧能力。
- `scripts/dev.py` 当前直接管理本机引擎、模型桥和桌面进程。未来仅将引擎启动/停止分成本地和 Docker 两条路径，不把远程服务器管理塞进此入口。
- `engine/python/project_installation.py` 当前仍要求本机 Python。Docker 模式不自动意味着宿主机可完全去掉 Python；若要减小本机依赖，须单独核对官方插件及辅助程序，暂不为缩包增加另一套实现。

## 后续：连接远程 Cognee

使用场景是同一个人在几台电脑上共用一个远程记忆库。Cognee 可运行在远程 Docker 内，Memlane 和日常编码 Agent 位于各自电脑。

连接远程后，App 阅读/搜索/管理与接入 Agent 指向同一远程服务，直接使用远程内容；本地库保留，切换不自动合并、迁移或在断线后静默回退。本轮不设计双向数据库同步。

同一项目在各电脑路径不同，需要明确关联到同一个远程项目。设备凭据应能分别撤销；不因此增加多人账号或组织体系。

安全连接候选为 HTTPS 加访问凭据；SSH 隧道或私有网络可作个人自托管选项。日常连接对象为记忆 API，不授予远程 Docker 管理权限。具体认证方式尚未定稿。

远程处理模型有两种讨论候选，均未实施：

- 在远程常驻机器部署并登录 Agent，Cognee 使用旁边的模型桥。
- 用户电脑上的 Memlane 主动建立出站连接，领取远程推理请求，调用本机 Agent 后返回；需要协调在线状态、请求身份、超时及结果核对，当前同步模型桥不能直接视为已有远程领取能力。

WebDAV 留作备份/导出同步的讨论候选，不作为远程 Cognee 的主访问或模型调用通道。离线编辑、多端合并及本地副本策略均未定稿。
