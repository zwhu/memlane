# UI 组件使用经验：先复用标准组件，再统一设计

2026-11-14。状态：问题已确认，组件替换与最终视觉验收尚未完成。

## 用户反馈与已证事实

用户原话：“你用的这些 弹框，下拉之类的都是自己手写的吗，有官方的组件库吗，有动画，有设计美感”。随后明确要求把组件问题作为经验记录。

本轮项目创建等界面使用了 `DialogBase`、`PopoverBase` 等基础组件并自行拼装外观。当前固定 MyGo v0.7.4 SDK 的 `docs/ui/dialog.md` 明确说明 `DialogBase` 是无外观的对话框；SDK 同时提供 `Modal`、`PopoverMenuButton`、`Select`、`Form` 及动效能力。不是没有官方组件可用，而是实施时没有优先复用和统一组件方案。并非所有控件都是手写：既有 Select、Checkbox 等已使用 SDK 控件。

用户连续指出重复入口、层级混乱、保存反馈难理解和弹框观感差。已证的实施问题是：在未先确定组件、主题和状态规范的情况下，按截图反馈逐处拼补；没有统一落实间距、字体、交互反馈及动效，也没有在交付前完成相应实际窗口视觉核对。不能据此认定所有问题都由 Base 组件导致；信息架构和文案也需要独立解决。

## 后续执行要求

1. 实施弹框、菜单、下拉、表单前，先检查当前固定 SDK 的官方成品组件、示例和仓库已有封装；选型依据当前版本，不能因网站新版存在能力就直接升级依赖。
2. 优先复用带完整交互和样式的官方组件，并统一主题、尺寸、留白、按钮层级和状态。确需使用 Base 时，先说明成品组件缺口，将样式和行为封装为可复用组件，避免在业务页逐处复制拼装。
3. 组件库不代替产品设计。先明确入口、字段、状态与动作，消除重复选择和技术术语；不能仅替换组件函数名就宣称重新设计完成。
4. 动效遵循 [MyGo 动效契约](../ui-redesign/motion-implementation.md)：统一时序、缓动与稳定 Key，支持减少动态效果，验证打断、关闭和重入；动效只表达真实状态，不模拟任务成功。
5. 先冻结一套可审阅的组件基线，再集中应用到相关界面。核对键盘焦点、Escape、遮罩关闭、禁用／加载／错误反馈和草稿保持；在实际 Native 窗口检查视觉。外屏不可用时，本轮用户已允许自带屏验收。
6. 编译、单测和合成截图分别记录；它们不能代替 Native 视觉验收。尚未完成就明确标记待验收，不把用户继续指出问题当作已交付后的装饰性优化。
