# 原始记录按会话与对话组织：调研

日期：2026-11-12。范围：回应用户对现有原始记录页“组织结构混乱、没有美感”的反馈，研究会话列表、对话阅读、Markdown 与历史时间线的分工。本文是研究与设计建议，不是已认可设计或工程完成记录；本轮不修改 App，不读取用户聊天库与 Agent 配置。

## 结论

建议把原始会话记录的主要浏览单位从“单条 user／assistant 消息”提升为“会话”，右栏按真实顺序呈现对话。Markdown 负责单条消息内部的排版；时间标签、日期分隔和跳转负责长会话导航。知识的修改历史另用版本时间线，不能混成聊天消息。

这是一项基于下列一手资料及用户反馈的产品建议。它不意味着已保存的片段足以重建完整会话；采集完整性、顺序、分支和授权仍需以 Memlane 实际数据为准。

## 外部一手资料核验

### 1. VS Code：把会话组织与会话内阅读分开

官方将 session 定义为 Agent 工作单元，chat 记录用户输入、Agent 回复、工具调用与上下文；支持的 harness 中一个 session 可有多个 chat。因此不能普遍把“同一个工作目录”当成“同一段对话”。分叉继承截至分叉点的历史，原会话仍可保留；分叉也不等于 Git 分支或工作区隔离。[官方会话概念](https://code.visualstudio.com/docs/agents/concepts/sessions)

阅读表现上，VS Code 区分 Markdown 字体与代码块字体、行高、换行；支持 sticky prompt 和可选时间戳。其会话视图模式允许把推理与工具调用收进折叠区，Compact 默认折叠已完成的调用组。这为“问答为主、执行过程可展开”提供了直接参考；相关进度设置部分仍标注实验性。[官方 Chat 阅读设置](https://code.visualstudio.com/docs/chat/chat-overview)

迁移到 Memlane 的建议：中栏选择会话，右栏阅读连续问答；工具过程是次级内容。不要直接复刻用于实时执行的权限确认、运行控制与输入框，因为 Memlane 当前讨论的是历史阅读。

### 2. Claude Code：列表展示有意义的会话，而不是日志条目

官方会话选择器展示名称／自动标题／摘要／第一条输入中的可用内容，并附最近活动、Git 分支和文件大小；分叉有独立 session ID。其 transcript 同时包含消息、工具使用／结果、请求记录与元数据，且内部 JSONL 格式会随版本改变。恢复后的上下文还可能从压缩标记处开始，不能把恢复视图等同于完整原始历史。[官方会话与 transcript 文档](https://code.claude.com/docs/en/sessions)

迁移建议：会话列表优先展示已有标题或首条有意义的用户文本，不默认调用模型重新生成标题。原始会话身份、消息身份和分支信息应独立保留；不依据相似标题或同目录自动拼接。若只保存片段，界面明确写“已保存的对话片段”，不能称“完整会话”。

### 3. assistant-ui：对话呈现可以分成独立组件

该项目把多会话管理做成 ThreadList，列出、切换和归档会话；单条 Message 则处理文本、图片、工具等内容分段。这证明“会话目录”和“消息呈现”可以分层实现，不必把原文解析、来源信息和列表布局塞进一个组件。[ThreadList](https://www.assistant-ui.com/docs/primitives/thread-list)、[Message](https://www.assistant-ui.com/docs/primitives/message)

Markdown renderer 独立处理标题、列表、链接、表格和代码块。因此“对话形式”和“Markdown 阅读”互相补充：前者表达谁说了什么，后者表达这段内容内部的层级。[Markdown text](https://www.assistant-ui.com/elements/markdown-text)

其分支组件用同级变体切换器表达重新生成的回答，只有单个分支时隐藏控件；不把多个互斥回答顺次拼成一段事实对话。[Message branches](https://www.assistant-ui.com/elements/message-branches)

长会话组件明确区分当前跟随底部与用户向上阅读：用户向上滚动后停止自动跟随，提供返回底部入口。对历史阅读，应进一步改成优先恢复已读位置或定位引用消息，而非每次打开都跳到最新。[Scroll anchor](https://www.assistant-ui.com/elements/scroll-anchor)

以上用于借鉴信息结构和交互规则；assistant-ui 是前端组件体系，不等于可直接装入 MyGo Native。

## 建议的 Memlane 阅读结构

| 层级 | 默认显示 | 按需展开 |
| --- | --- | --- |
| 项目原始记录列表 | 按日期分组的会话；标题／首句、Agent、最近时间、已保存消息数 | 会话身份、来源范围；无可靠身份的材料独立列出 |
| 会话顶部 | 主题、项目、Agent；必要的片段／缺失提示 | 工作目录、session ID、采集渠道、来源时间与保存时间 |
| 对话正文 | 真实角色、连续消息、Markdown；必要时间分隔 | 单条来源、原始文本、可用的工具过程 |
| 阅读工具栏 | 查找、上一处／下一处、复制 | 完整来源与导出选项，具体范围另定 |
| 知识修改历史 | 版本、修改者、时间、变化摘要 | 差异与版本正文；与对话视图区分 |

视觉建议：在阅读区采用稳定的左侧角色标记／头像，用户消息用克制浅底色，Agent 长回答以白底、左对齐的宽阅读区展开；不把所有消息都做成宽大左右气泡或独立卡片。日期与较长时间间隔作为轻分隔，不给每句话强加时间轴线，避免每条消息重复一整块元数据。此为设计提案，需要实际样稿比较，尚未认可。

首版建议保持只读历史，不加输入框，不承诺继续原 Agent 对话。文档、日志等非会话原始记录仍使用文档阅读；知识修改历史保持既有历史弹框承载，是否增加版本时间线单独评审。

## 数据可信度规则与未验证项

以下是本次建议，不能被误写成外部产品或 Memlane 已实现能力：

1. 只聚合有可靠来源身份且属于当前授权范围的记录；会话 key 至少隔离项目／来源 Agent 或连接身份，不能只用目录名。
2. 有原生消息序号、父消息关系时优先采用；时间戳相同、缺失或仅是采集时间时，不伪装成精确对话顺序。必要时标明“按保存顺序”。
3. 保存片段不推断其间没有其他消息。不生成虚假的“缺失 N 条”；仅有证据时显示具体缺口，没有证据时给范围级片段提示。
4. 多条 assistant 消息可连续出现，不强行一问一答配对；工具返回不冒充 Agent 回答，未采集的工具内容不凭文本推断。
5. 有明确分支身份才展示分支选择；没有身份时不依据文本相似度猜测。
6. Markdown 改变呈现，不改写保存文本；保留复制原文和查看原文。链接、HTML、图片加载行为需在组件选型后明确验证。
7. 长会话分段加载时使用稳定消息身份保持滚动锚点；搜索命中打开相应会话并定位到消息。跨消息选择、查找高亮、代码复制、长表格和宽代码块需真实 Native 验证。

## 建议的下一步

先用合成材料制作一个会话阅读样稿：普通问答、Markdown 长回答、连续 Agent 消息、仅保存片段、未知原始时间及窄窗口。另做一个知识版本时间线样稿，让用户比较两种历史各自的表达。认可后再改变现有页面；不得把本报告当作开始实现或重读用户历史的授权。

## 本地实现与 MyGo 能力

本轮只读核对 `go.mod` 锁定的 MyGo v0.7.4 及本地模块源码，未构建或运行新窗口。

- 当前原文阅读器使用 `ui.Text`／`ui.RichText` 显示正文，并非 Markdown 阅读器，见 [阅读实现](../internal/desktop/source_reader_presentation.go)。
- v0.7.4 的 `ui/markdown` 已提供 `View`、主题、代码高亮／复制／横向滚动、选择与 Markdown 复制、`ShareSelection`；其 `examples/markdown-chat` 演示稳定消息 key、列表和用户消息／Agent Markdown 回复。这是源码能力，不是 Memlane 已集成或实际窗口验收。可参考[官方 Markdown 文档](https://mygo.egoist.dev/docs/ui/markdown)，但当前网站显示 0.9.0，新增 API 不外推到锁版本。
- [Codex 消息解析](../internal/agents/codex_capture.go)限定 user／assistant，明确不采集工具结果和 reasoning；[持久化适配](../internal/agents/codex_capture_runtime.go)保留 session、turn、message、role、timestamp、timestamp_kind 等来源字段，却把会话信息拼入正文，再以 `Source.Fragment` 保存元数据 JSON。用户消息时间标为 hook 观察时间，不能当作原始发送时间。
- 这些身份字段是会话分组的基础，不足以证明完整性、分支或精确全局顺序；现有条目列表 API 仍是逐记录分页。分组查询、可靠排序及搜索定位到消息需要单独设计。不能只把当前页的条目拼起来就称完整会话。
- 新阅读层应保留原始正文与出处；不要按任意正文前缀猜角色并删掉用户文本。旧包装格式需要有明确来源标识的兼容解析或独立展示字段，具体迁移方案未验证。

## 采集复用问题：2026-11-12 用户追问

**后续用户已确认方向**：所有 Agent 采集统一使用官方方案；只有无官方方案才参考官方插件补适配，Memlane 负责把插件安装到对应 Agent。此项从研究建议提升为已确认规则，见[接入契约](ui-redesign/agent-connection-contract.md#2026-11-12-用户确认所有-agent-采集统一复用官方方案)。迁移可行性与实际安装结果仍待工程验证。

用户问：既然 Cognee 插件会采集，为什么 Memlane 另做？

已证实的事实：

1. 固定上游 `997fd6f` 的 [Cognee Codex 插件说明](https://github.com/topoteretes/cognee-integrations/blob/997fd6f72253aa97b49996eb1b032793f0257935/integrations/codex/README.md)明确具备 prompt、工具轨迹和助手回复采集，以及会话结束同步能力。
2. Memlane [既有首任务流程](agent-first-task-flow.md)明确由官方插件负责采集与官方提炼，Memlane接收材料、维护当前知识与出处；不能说项目从未复用官方采集。
3. 当前 [日常采集账本](engineering/codex-daily-capture-20261111.md)则实施自有 UserPromptSubmit／Stop hook、解析器、暂存及归属链路，且没有工具轨迹采集。这是另一条实现。
4. 所查日常采集账本未提供“官方插件不能满足需求”的逐项比较或排除复用证据。独立授权、离线保留、项目归属与版本回执是实际产品要求，但本身不证明必须自建消息采集器。

研究判断：应先评估复用官方采集及其会话／trace输出，在接收侧适配 Memlane 的授权、归属、回执和阅读模型。保留自有采集是否必要，须用官方输出的消息完整性、稳定身份、顺序、断网行为、提炼与采集是否可解耦及现有服务集成的实证决定；本轮没有完成该替换可行性验证，不自动换装或双重采集。
